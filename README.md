# LiteLLM gateway starter for Railway

One OpenAI-compatible address in front of every provider you use, with virtual
keys, budgets and rate limits that are actually enforced — because the database
and Redis they need are wired in.

## Why this exists

Self-hosted AI gateways are the fastest-growing thing people deploy on Railway
right now, and the fastest-failing: the most popular one took 1700 installs in
six weeks with a third of them not coming up. The mature alternative, LiteLLM,
is packaged as a single container in every template that offers it — and a
single container is exactly what LiteLLM cannot be if you want the features
people install it for.

Without Postgres there are no virtual keys, no budgets and no spend tracking.
Without Redis, rate limits are counted per process, so two replicas quietly
enforce twice the limit you set, and the cache is duplicated per replica.

This template is the three services wired together, with the settings that make
them cooperate.

## What you get

- **An OpenAI-compatible endpoint** at `/v1` — point any OpenAI SDK at it by
  changing the base URL.
- **A web UI** at `/ui` for adding providers, issuing keys and reading spend.
- **Virtual keys** with per-key budgets, model allow-lists and RPM/TPM limits,
  stored in Postgres.
- **Shared limits and cache** in Redis, so the numbers hold no matter how many
  replicas you run.
- **Fallbacks and retries** between providers, so one provider's outage is not
  yours.

## After deploying

1. Open `/ui` and sign in with the generated `LITELLM_MASTER_KEY`.
2. Add a provider under **Models** — your own API key goes there, encrypted at
   rest with `LITELLM_SALT_KEY`.
3. Issue a virtual key per person or per application. Give each one a budget.
4. Delete the `self-test` model once you have your own.

The `self-test` model answers without calling any provider. It is there so a
fresh deployment can be verified before you have added a key — and so the check
below has something to call.

## Prove it works

```bash
scripts/verify-gateway.sh https://your-gateway.up.railway.app sk-your-master-key
```

It creates a virtual key with a limit of one request per minute, spends it,
confirms the second call is refused, reads the key back out of the database, and
adds a model at runtime. Then it deletes what it created.

## Configuration

| Variable | Required | Purpose |
|----------|----------|---------|
| `LITELLM_MASTER_KEY` | yes | Admin credential; also the UI password. Generated by the template |
| `LITELLM_SALT_KEY` | yes | Encrypts stored provider keys. **Changing it makes existing stored keys unreadable** |
| `DATABASE_URL` | yes | Postgres — keys, budgets, spend, models |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | yes | Shared limits and cache |
| `STORE_MODEL_IN_DB` | no | On by default, so models added in the UI survive redeploys |
| `UI_USERNAME` / `UI_PASSWORD` | no | A separate UI login, if you would rather not hand out the master key |

Provider keys (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, …) can be set as variables
too, and referenced from the UI as `os.environ/NAME`.

## What is pinned, and why

The image is pinned to `ghcr.io/berriai/litellm-database:v1.103.2`. LiteLLM ships
several releases a week; a moving tag turns a working deployment into a lottery
on every restart. The `-database` variant carries the Prisma toolchain, so the
proxy migrates its own schema on first boot rather than needing a separate job.

When you upgrade, change the tag in the Dockerfile — deliberately, and with a
backup of the database.

## Scaling note

Adding replicas is safe: keys, spend and limits live in Postgres and Redis, not
in the process. Set `DISABLE_SCHEMA_UPDATE=true` on the extra replicas so they
do not all try to migrate the schema at once.
